where-unknown | Explain why a SQL WHERE predicate that evaluates to UNKNOWN does not retain the row. | WHERE keeps rows for which the predicate is TRUE; NULL-related comparisons may produce UNKNOWN, which is not TRUE and is filtered out. | UNKNOWN means the database has no reason to reject the row, so WHERE retains it until the value becomes known. | Gives the truth-value selection rule and connects it to null comparisons. | Invents deferred inclusion semantics that WHERE does not have. | SQL's three-valued logic distinguishes TRUE, FALSE and UNKNOWN. A WHERE clause retains rows only when its predicate is TRUE. Ordinary comparisons involving NULL often produce UNKNOWN, so they do not behave like a comparison against an ordinary sentinel value. Write explicit IS NULL or IS NOT NULL conditions when absence belongs to the selection rule and test those rows separately.
count-expression | Explain how COUNT(column) differs from COUNT(*) when the column contains NULL. | COUNT(column) counts non-null expression values, whereas COUNT(*) counts rows, so rows with a null column contribute only to the latter. | Both forms count every row; choosing a column merely tells the optimizer which index to read. | Distinguishes expression-value counting from row counting. | Treats a semantic difference as a performance-only choice. | COUNT(*) reports the number of rows in its input group. COUNT(expression) reports the number of non-null values of that expression. These coincide only when the expression is non-null for every input row. Choose the form based on the question being asked, especially after outer joins. Include a group with null values and a group with no matching child values in validation fixtures.
not-in-null | Explain why a nullable value in a NOT IN subquery can change the expected exclusion result. | The comparison against a null member can make NOT IN UNKNOWN rather than TRUE, so use a null-aware formulation such as an appropriately correlated NOT EXISTS when that matches the intended rule. | A null subquery member is automatically ignored by NOT IN, so it cannot change whether an unmatched value is retained. | Identifies the unknown comparison and a conditional alternative. | Assumes null members are discarded without affecting truth values. | NOT IN follows comparison and three-valued-logic rules. A null in its comparison set can prevent an otherwise unmatched value from yielding TRUE. Decide how absent values should behave, then express that decision explicitly. A correlated NOT EXISTS is often useful but must implement the actual matching rule. Test nulls on both sides rather than replacing syntax without considering the desired semantics.
null-group | Explain why grouping rows by a nullable field can put null-valued rows into one group even though ordinary NULL equality is not TRUE. | SQL grouping uses its grouping equivalence rules rather than ordinary equality truth evaluation, so null-valued grouping keys can share a group. | Every null-valued row must form its own group because NULL = NULL is not TRUE. | Separates grouping semantics from a scalar comparison predicate. | Applies ordinary comparison behavior as if it defined grouping partitioning. | GROUP BY does not partition rows by repeatedly asking whether ordinary equality returns TRUE. Its grouping rules place null-valued instances of a grouping key together. This can create a large missing-value group that deserves explicit interpretation in a report. Validate grouping output alongside counts of missing data, and avoid describing the resulting bucket as a real category unless the domain defines it that way.

outer-join-filter | Explain how placing a predicate on the nullable side in WHERE can remove unmatched rows from a left join. | Unmatched rows have null-extended right-side fields, so a right-side predicate in WHERE may be UNKNOWN and filter them; put matching restrictions in ON when unmatched left rows must remain. | A LEFT JOIN preserves all left rows regardless of any later WHERE clause, so right-side filtering cannot remove them. | Connects null extension to filtering and qualifies predicate placement by intent. | Ignores filtering that happens after the join result is formed. | A left join first forms matched rows and null-extended rows for unmatched left inputs. A subsequent WHERE condition still filters that result. Predicates on the right-side fields can therefore eliminate unmatched rows. Place restrictions according to the intended question: ON controls matches, while WHERE controls retained result rows. Test one matched and one unmatched left row before relying on a count or report.

nullable-join-key | Explain why two missing keys do not match through an ordinary equality join and when an explicit null-safe rule is needed. | NULL = NULL evaluates to UNKNOWN, so an equality join does not treat two absences as a match; use explicit null-safe semantics only if the domain says those rows belong together. | Missing keys are equal by definition, so an ordinary equality join automatically joins all null keys to one another. | Gives the comparison behavior while making the alternative dependent on domain intent. | Assumes missingness establishes a shared key identity. | Ordinary equality joins do not match two NULL keys merely because both values are absent. Whether absences should match is a domain decision, not a default identity rule. A null-safe comparison can express that decision but may create many-to-many matches among missing values. Test the expected multiplicity and avoid grouping unrelated entities solely because neither has an identifier.
check-unknown | Explain why a SQL CHECK expression can need an explicit NOT NULL requirement to prohibit absent values. | In common SQL CHECK semantics, UNKNOWN does not violate the check, so a positive-value expression alone can allow NULL; add the intended non-null constraint explicitly. | CHECK(amount > 0) necessarily rejects NULL because NULL is not a positive number in ordinary arithmetic. | Identifies how constraint acceptance differs from WHERE selection. | Assumes mathematical intuition determines the three-valued constraint result. | CHECK constraints and WHERE clauses use their results for different purposes. Under common SQL CHECK semantics, a constraint fails when its expression is FALSE; UNKNOWN can pass. A positivity check therefore need not prohibit NULL. If the field must be present and positive, express both requirements and verify them on the selected database. Include an absent value in the constraint test fixture.
