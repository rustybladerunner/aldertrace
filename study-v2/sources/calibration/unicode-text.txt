canonical-equivalence | Explain how canonically equivalent text can have different code-point sequences and what that means for byte comparison. | A precomposed character and a base-plus-combining sequence may represent equivalent text but have different bytes; normalize to an agreed canonical form before an equality policy that requires it. | If two strings render as the same accented word, their bytes must match because fonts choose appearance after equality is decided. | Identifies multiple encodings of equivalent text and a suitable normalization boundary. | Assumes visual equivalence implies identical storage. | Unicode can represent some text with either a precomposed character or a sequence containing a combining mark. These sequences need not be byte-identical. When canonical equivalence belongs to the application's equality contract, normalize consistently at a specified boundary. Preserve the original input when required for display or provenance. Normalization is not a general solution to look-alike characters or locale-sensitive collation.
grapheme-cursor | Explain why moving a text cursor by one code point can split what a user perceives as one character. | A displayed grapheme may contain several code points, so editing navigation should use the intended grapheme-boundary rules instead of blindly advancing one code point. | Every Unicode code point is one visible character, so code-point indexing always gives natural cursor movement. | Separates code points from user-perceived grapheme clusters. | Incorrectly assumes a one-to-one mapping between code points and displayed characters. | Code points are encoding units of meaning, while a grapheme cluster can combine several of them into a user-perceived character. A cursor or deletion operation that steps by code point may separate marks or pieces of a joined sequence. Choose explicit segmentation behavior for the editor and test combining marks and joined symbols. Storage offsets and editing positions need not use the same units.
casefold-length | Explain why case-insensitive matching cannot assume case folding preserves string length. | Some characters fold to multiple code points, so folded indices and lengths may differ from the original; preserve an offset mapping when highlighting matches. | Case folding merely flips one bit per character, so offsets in the folded string can always index the original unchanged. | Names expansion and its concrete effect on offset-based features. | Assumes both a simplistic representation and length preservation. | Case folding supports caseless comparison but is not necessarily a one-code-point substitution. A folded string can have a different length from its source. If search operates on transformed text and then highlights the original, maintain an appropriate position mapping. Test expansions and combining sequences rather than validating only ASCII. Lowercasing for display and case folding for matching are distinct operations.
locale-casing | Explain why user-facing uppercasing may need a locale rather than a universal ASCII-style mapping. | Language-specific casing rules can differ, so a fixed ASCII transformation may produce the wrong letters for a user's language. | Alphabetic case is universal; applying the English ASCII mapping to every script preserves the correct local spelling. | Identifies locale-dependent conventions and the limitation of a universal mapping. | Generalizes a narrow mapping to languages it cannot represent correctly. | User-facing casing follows language conventions that may not match a default mapping. Locale-sensitive formatting should receive the intended language context rather than infer it from a few characters. Do not apply display-casing rules as an unexamined identifier-equality policy. Test the supported locales with representative non-ASCII examples and document behavior when locale information is absent.
bidi-source-order | Explain why the displayed order of mixed-direction text cannot be assumed to equal its stored logical order. | Bidirectional layout can reorder the visual presentation, so selection, debugging and validation should distinguish the logical code-point sequence from what is drawn. | Copy the left-to-right screen positions as source order because rendering never rearranges the underlying sequence. | Describes presentation reordering without treating it as a storage rewrite. | Assumes rendered positions reveal the stored sequence directly. | Mixed-direction text is stored in logical order and laid out according to directional rules. The visible order can differ from that logical sequence. Tools that inspect identifiers or structured text should make directional controls and logical contents inspectable where necessary. Test editing and selection behavior with mixed-direction examples. A screenshot alone cannot establish the sequence a parser received.
decoder-replacement | Explain why silently replacing invalid byte sequences can erase distinctions that an input-validation boundary needs. | Replacement decoding can map different invalid inputs to the same replacement character, so a strict boundary should reject malformed encoding when preserving those distinctions matters. | Replacement characters retain the exact original invalid bytes, so validation after replacement has all the same information as validation before it. | Explains the many-to-one transformation and when rejection is needed. | Falsely claims lossless recovery from generic replacement characters. | Text decoders may reject malformed byte sequences or replace them. Replacement is useful for tolerant display, but can discard which bytes were malformed and make distinct inputs look alike. Select the behavior at the boundary according to the contract. Preserve raw bytes separately if diagnostics require them, and do not assume a successfully decoded replacement string proves the original encoding was valid.
stream-boundaries | Explain why a streaming UTF-8 decoder may need to retain bytes between input chunks. | A multibyte sequence can be split across chunks, so the decoder must keep an incomplete suffix and finish it when the next bytes arrive. | Each transport chunk must be a complete UTF-8 string; decode chunks independently and replace any unfinished suffix immediately. | Identifies arbitrary transport segmentation and the required decoder state. | Assumes chunk boundaries align with encoded characters and loses split sequences. | A transport's chunk boundaries need not align with UTF-8 character boundaries. A streaming decoder keeps enough state to complete a partial sequence from the next chunk. At the end of the stream it must handle an unfinished sequence according to the declared error policy. Test every split position in representative multibyte strings, rather than only inputs delivered as one complete buffer.
byte-limits | Explain why a maximum UTF-8 byte length is not the same constraint as a maximum character count. | Encoded characters can occupy different numbers of bytes, so a storage byte limit requires measuring the encoded form rather than counting displayed characters. | Any string of fifty characters fits a fifty-byte UTF-8 field because Unicode standardizes character size. | Connects variable-width encoding to the actual storage constraint. | Assumes a fixed one-byte representation for all Unicode text. | Storage and protocol limits often apply to encoded bytes. UTF-8 uses different byte lengths for different code points, and user-perceived characters can contain several code points. State which unit a limit uses and measure at that boundary. If truncation is permitted, avoid splitting an encoded sequence or an interaction-relevant grapheme. Test non-ASCII and combining sequences near the limit.
compatibility-normalization | Explain why compatibility normalization requires a deliberate product decision rather than being interchangeable with canonical normalization. | Compatibility normalization can collapse distinctions such as presentation variants that the application might need to preserve, so its broader equivalence policy must be intentional. | All normalization forms preserve every distinction; choosing a compatibility form only changes processing speed. | Identifies potentially meaningful collapsed distinctions and the need for a chosen equality policy. | Misrepresents normalization forms as semantically interchangeable. | Compatibility normalization intentionally folds some distinctions beyond canonical equivalence. That can be appropriate for a search key while being inappropriate for archival text or an identifier contract. Choose the form according to the application's semantics and retain original text when needed. Test examples whose distinctions matter to the product; normalization is a policy choice rather than a universal cleanup step.
confusable-letters | Explain why canonical normalization does not by itself eliminate look-alike characters from different scripts. | Visually similar letters can be distinct code points without canonical equivalence, so normalization alone cannot implement a policy against cross-script confusables. | Normalizing to NFC merges every character with the same visible shape, making mixed-script look-alikes impossible. | Separates canonical equivalence from visual resemblance. | Attributes visual-confusable folding to a normalization form that does not provide it. | Characters from different scripts can look similar while remaining distinct Unicode characters. Canonical normalization does not merge all visually confusable text. An application concerned with misleading identifiers needs an explicit policy, potentially including script restrictions or confusable analysis appropriate to its users. Avoid treating such a policy as a general restriction on ordinary multilingual prose, and test legitimate language use as well as misleading examples.
