focus-return | Explain where focus should go after a modal closes and why an unavailable opener needs a fallback. | Return focus to the control that opened it so the user resumes in context; if that control disappeared, select a logical surviving destination. | Always send focus to the page's first link because its existence is more important than the user's interrupted position. | Preserves the user's place and handles removal of the original target. | Provides a fixed destination unrelated to the user's workflow. | Opening a modal interrupts a user's position in the page. Save the invoking control and normally restore focus there on close. If the operation removes that control, choose a nearby logical destination instead of focusing a detached node. Test cancel, confirm and removal paths with the keyboard, checking both the active element and the next useful action.
tab-order | Explain why visual rearrangement alone does not guarantee a matching keyboard focus order. | Sequential focus generally follows document order and focusability rules, so CSS placement can put the visible arrangement out of step with keyboard traversal. | Moving a button with CSS also moves its place in Tab order, so DOM order cannot affect keyboard use. | Identifies the distinct mechanisms behind visual and sequential focus order. | Assumes CSS positioning rewrites sequential navigation order. | Visual layouts can reorder items without changing their document order. Keyboard users may then traverse controls in an order that jumps around the screen or obscures dependencies. Prefer a logical source order and check responsive arrangements. Positive tabindex values add a separate ordering system and usually make maintenance harder; use them only with a justified, tested interaction contract.
button-semantics | Explain why using a native button usually requires less custom keyboard behavior than styling a generic container as clickable. | Native buttons already provide focusability, activation semantics and disabled behavior; a generic element needs those behaviors implemented and tested explicitly. | A click listener makes a div equivalent to a button for keyboard and assistive-technology users. | Connects the element choice to concrete built-in interaction behaviors. | Equates pointer-click handling with the complete button contract. | A control's appearance does not provide its interaction semantics. Native buttons participate in keyboard focus and expose button behavior to user agents. A generic container with a click handler lacks parts of that contract unless they are implemented explicitly. Use the native element where possible and verify its accessible name, focus appearance and disabled behavior in the actual interface.
focus-indicator | Explain why removing the browser outline requires a visible replacement focus indicator. | Keyboard users need to locate the active control before activating it; removing the outline without another clear indicator hides that location. | Hover styling is an adequate replacement because a keyboard user's mouse pointer remains on the focused control. | Names the lost information and the affected interaction. | Incorrectly assumes pointer position follows keyboard focus. | A visible focus indicator tells users which control will respond to their next keyboard action. It must remain perceivable against the actual background and should not be clipped by surrounding containers. If replacing the default outline, provide a clear alternative. Test keyboard navigation through every control rather than checking only pointer hover states or a static screenshot.
roving-focus | Explain how roving tabindex reduces Tab stops inside a composite widget while preserving internal keyboard navigation. | One item is in the page Tab sequence and the others use tabindex -1; the widget moves focus with its documented keys and updates the active tab stop. | Set every item to tabindex -1 and omit internal key handling; then Tab can still visit them in their displayed order. | Includes both the external entry point and internal navigation responsibility. | Removes the entry points and assumes keyboard navigation that has not been implemented. | Composite widgets can provide one Tab stop while using arrow keys for movement within the widget. Roving tabindex changes which item has tabindex zero and moves focus as selection or active position changes. This requires a consistent widget-specific keyboard contract. Test entry, exit, disabled items and dynamic removal; changing tabindex alone does not implement the interaction.
hidden-controls | Explain why visually hiding an interactive element may leave a keyboard navigation problem. | Some visual hiding techniques leave the element focusable, so Tab can land on an invisible control; remove unavailable controls from interaction as well as view. | A transparent control is harmless because users cannot click what they cannot see, and keyboard focus follows visibility automatically. | Distinguishes appearance from focusability and calls for consistent availability. | Ignores invisible keyboard targets and assumes transparency changes focus rules. | Opacity, off-screen positioning and clipping can hide a control visually without removing it from sequential focus. That can leave a user apparently stuck on an invisible target. Select a hiding technique appropriate to whether content should remain accessible, and disable or remove interaction when the control is unavailable. Inspect keyboard traversal while menus and panels are closed.
escape-dismissal | Explain why an Escape handler for a dismissible popup should be scoped to the active interaction. | A scoped handler closes the relevant popup without letting stale listeners dismiss unrelated UI or process the same key repeatedly. | Leave one permanent document handler for every popup ever opened; all of them can safely react to Escape together. | Identifies stale and competing handlers as the reason for interaction-scoped handling. | Intentionally accumulates global reactions with no ownership or cleanup. | Dismissal keys belong to an interaction with a defined owner. Register or activate handling when that interaction is present, and clean it up when it ends. Nested overlays need a clear rule for which layer handles Escape. Test repeated opening and closing and verify that one key closes only the intended layer while preserving a useful focus destination.
disabled-links | Explain why marking a link with aria-disabled alone does not stop its native activation. | The attribute communicates a state but does not remove href behavior; the implementation must prevent unavailable activation and choose suitable focus behavior. | aria-disabled cancels navigation in every browser, so leaving the href active cannot trigger the destination. | Separates communicated semantics from browser interaction behavior. | Attributes an automatic behavior change to a semantic attribute. | An ARIA state describes a control to accessibility APIs; it does not generally implement interaction behavior. A link with aria-disabled can still navigate through its href unless the application prevents that activation. Decide whether an unavailable action should remain discoverable in the focus order, then implement and test keyboard and pointer behavior consistently with that decision.
focus-on-update | Explain why moving focus on every background data refresh can disrupt keyboard work. | Refreshes are unrelated to the user's navigation and can steal focus mid-action; preserve the current location unless the workflow requires an explicit move. | Focus should jump to the newest data after every refresh because newer information always deserves priority over an in-progress action. | Connects asynchronous updates to interruption of the current task. | Treats recency as permission to disrupt the user's interaction. | Background updates can occur while a user is typing or navigating. Automatically focusing the updated area changes the destination of subsequent keystrokes and can make the interface unpredictable. Preserve focus for routine refreshes and communicate changes through an appropriate non-disruptive mechanism. Move focus only when an explicit user action or required workflow transition makes the destination meaningful.
keyboard-test | Explain why pointer-only end-to-end tests cannot establish that all controls are operable from the keyboard. | Pointer tests bypass focus order and key activation, so keyboard traversal and activation need direct tests of their own. | If every control responds to click automation, keyboard operation follows automatically from sharing the same event handler. | Identifies interaction paths the pointer tests never exercise. | Assumes shared click handling proves reachability and key behavior. | Pointer automation can successfully click an element that a keyboard user cannot reach, cannot identify as focused, or cannot activate with expected keys. Add tests that enter the page, traverse controls and complete the intended task with keyboard input. Include open and closed overlays and dynamic content. Check actual focus state as well as whether the final business action occurred.
